# Independent encrypted image backups

**Selected configuration: restic to a private Backblaze B2 S3-compatible bucket in a separately administered account.** The provider account, region, budget and recovery custodian require owner approval. A local encrypted repository using real staging fixture bytes was successfully recovered. Off-site operation and disaster recovery remain unverified.

| Option | Cost and operational considerations |
| --- | --- |
| Backblaze B2 | Published starting rate $6.95/TB-month and egress allowance up to three times stored volume. S3 compatibility, scoped credentials and optional Object Lock fit independent backup. Choose protection periods and retention credentials carefully so a writer cannot erase every recoverable version. [Pricing](https://www.backblaze.com/cloud-storage/pricing) · [Object Lock](https://www.backblaze.com/docs/cloud-storage-object-lock) |
| Cloudflare R2 Standard | Published storage rate $0.015/GB-month, operation charges and free internet egress. S3-compatible private storage also supports the chosen client-encrypted format; a useful option if the owner already operates a separately administered Cloudflare account. [Pricing](https://developers.cloudflare.com/r2/pricing/) · [Durability](https://developers.cloudflare.com/r2/reference/durability-and-reliability/) |

Both can store durable copies independently of Supabase. The application-level digests and encrypted repository allow a restore to be verified independently of provider checksums. Pricing excludes taxes and depends on actual usage.

## Setup and runbook

- On a trusted Linux backup worker install Node, restic, mountpoint and the project release under `/opt/visiontech`. Create the dedicated `visiontech-backup` OS account and mount a private encrypted scratch volume. Point `VISIONTECH_BACKUP_SCRATCH` at its mountpoint. Configure restic's cache in an appropriate private writable location. Do not run the backup job in the public upload service.
- In `/etc/visiontech/backup.env`, using restricted file permissions, configure the staging `SUPABASE_URL`, server credential, `RESTIC_REPOSITORY=s3:https://<regional-S3-endpoint>/<private-bucket>/<dedicated-prefix>`, provider `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, and `RESTIC_PASSWORD_FILE`. Mount the password file from a separate secret store and escrow recovery access with the named owner. Initialize only the newly approved, dedicated repo with `restic init`. [Repository setup](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html)
- Coordinate a quiet edit/review window and matching database recovery point before export. The existing exporter writes registered originals, normalized JPEGs and registry metadata. The new companion records product IDs, models, attachment order, visibility and row version. A missing or cross-model attachment fails verification. Pair with a consistent database backup covering identities, full products, audit history, migrations and policies. The media snapshot is not a transactionally consistent whole-database backup. Inventory unregistered keys separately.
- Install the supplied systemd service and two timers. Daily export is scheduled for 01:00 UTC and a monthly full read-and-restore drill for 04:00 UTC on the first. Configure operator alerts for failed or missed jobs. Jobs were not installed on a hosted machine. `backup.sh backup` creates a fresh protected scratch directory, verifies the snapshot, encrypts it with restic and checks the repository. Retention defaults to a dry run. After the owner validates the scope, lock policy and recovery point, `VISIONTECH_APPLY_RETENTION=true` enables scoped retention and pruning for 30 daily recovery points. Missed backup days cannot be recovered by retention. [Retention semantics](https://restic.readthedocs.io/en/stable/060_forget.html)
- `backup.sh verify` performs a full repository data check, restores the latest tagged snapshot to fresh scratch, verifies original/derivative sizes and SHA-256, and checks all media attachments. For an application recovery drill, restore matching database dependencies to disposable Supabase, create the private bucket with its approved policies, then use the existing `restore-local` utility with a loopback target. Verify private preview and publication/withdrawal behavior before any separately authorized operational restore.
- The rehearsal exported two synthetic media records and four byte files plus attachments. The encrypted repository passed `restic check --read-data`, restored to a fresh directory and matched every exported file. The snapshot verifier separately rejected corrupt bytes and a wrong-model attachment. Acceptance still requires a fresh read from the independent B2 account and recovery using the custodian's escrowed secret. [Execution evidence](PRODUCT_MANAGEMENT_FINAL_TEST_REPORT.md)
