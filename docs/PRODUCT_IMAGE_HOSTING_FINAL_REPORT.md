# Staging image upload hosting

**Selected configuration: one long-lived Render Docker web service.** It serves the packaged staging frontend and existing Node API on a single HTTPS origin. Vercel production routing requires no changes. The Linux image built and ran locally. No Render account, paid resource, public origin or DNS record was provisioned.

The existing transport accepts a 4 MiB binary image inside a bounded JSON/base64 request of up to 5,700,000 bytes. Vercel Functions document a 4.5 MB payload limit. Longer function time or response streaming would not make that request fit. The new host keeps bounded request buffering, isolated Pillow decoding, and direct HTTPS Storage writes. Original and derivative survive app restarts. The choice also preserves the existing in-process session store: run **one** instance, and expect restarts to sign users out. [Vercel limits](https://vercel.com/docs/functions/limitations) · [Render Blueprint reference](https://render.com/docs/blueprint-spec)

## Owner configuration

1. Select the staging workspace, region and spending cap. The Blueprint selects the always-running Starter instance. Confirm current compute, bandwidth and build pricing before authorizing billing. Provide the reviewed source through an owner-approved release mechanism. The files are local and were not pushed. [Render pricing](https://render.com/pricing)
2. Use `deploy/staging/render.yaml` as the Blueprint path. Docker context is the project root. The Dockerfile-specific ignore list excludes environment files and archival photographs from the build context. The runtime serves vetted static routes only. The staging listener binds the supplied `PORT`. Pillow is installed in the image; the runtime uses `VISIONTECH_PYTHON=/usr/bin/python3`.
3. Set `APP_ORIGIN` to the exact HTTPS origin with no trailing slash. Set the staging `SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_SECRET_KEY` in the host secret manager. The target URL is fixed to the approved staging project. The Blueprint generates `RATE_LIMIT_HASH_SECRET`. No backup credential belongs here. Proxy trust defaults off. Keep the staging mail worker and sender configuration outside this verification.
4. Check `/api/health`, same-origin session cookies and origin validation. Keep `STAGING_PRODUCT_EDITOR_ENABLED=false` for ordinary access. In an owner-controlled acceptance environment, authorize test access, exercise the editor with disposable identities, and leave the ordinary hosted editor enabled only after the recovery and rights gates pass.
5. Check a valid 4 MiB upload, malformed/oversize rejection, ingress timeout and retry at the hosted boundary. The server accepts up to 60 seconds to receive a request; the upload UI allows 90 seconds. Storage calls and image processing have separate timeouts. Immutable hash-addressed keys and digest checks make retries safe. Confirm archive/withdrawal still removes public access immediately on a fresh request.

The staging container has no requirement for durable local disk. Public image delivery rechecks eligibility, checks the derivative hash and sends private/no-store. Suspending a product or withdrawing an approval cannot recall bytes already saved by a visitor. [Staging workflow tests](PRODUCT_MANAGEMENT_FINAL_TEST_REPORT.md)
