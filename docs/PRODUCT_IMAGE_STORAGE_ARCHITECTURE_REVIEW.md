# Product image storage and commercial publication review

**23 November 2026. Recommendation:** keep new hosted uploads disabled until the API stores photographs in durable shared storage. For a Vercel frontend and the existing Supabase backend, use a private Supabase Storage bucket and a same-origin media endpoint that checks publication state. VisionTech-Staging currently has **zero buckets**. No image or bucket was created, changed or deleted during this review.

## What the implementation does today

| Property | Finding |
| --- | --- |
| Write and read locations | POST /api/admin/products/images writes under the API checkout at `assets/images/products/managed/{MODEL}/{sha256}.jpg`. The public renderer resolves the relative path on the **website origin**. A separate frontend host does not automatically see the API's files. Saving gallery paths also calls local filesystem stat. |
| Restart behavior | Files on persistent host storage survive a Node process restart if the same directory is retained. An image rebuild, ephemeral container, separate replica or static redeployment can lose or hide them. No durable volume mount or restart/restore test was evidenced here. |
| Authorization | The existing session, active ADMIN/SUPER_ADMIN role and origin checks run before uploads. The backend requires a true model/rights attestation. The uploader may prepare a photograph before a product exists. The current implementation has no per-asset approval record containing a rights document, approver or timestamp. |
| File checks | Server accepts JPEG, PNG and WebP with a 4 MiB decoded-input limit and bounded JSON body. Python/Pillow checks the decoded format against the declaration, rejects multiple frames, imposes a 12-million-pixel threshold, applies EXIF orientation, strips metadata and emits JPEG within 1800 × 1800. Transparency is flattened on white. Original bundled files are preserved. |
| Replacement and concurrency | SHA-256 of normalized bytes and exclusive create prevent normal overwrites. Identical normalized bytes reuse the key. A different photograph gets a new URL. The current EEXIST branch trusts the existing file without rechecking its contents. Atomic completion and digest verification would protect against a partial file left by an interrupted write. |
| Detach, archive and delete | Detaching a photo, abandoning an upload or archiving the product leaves the file on disk. A static URL can still serve draft, archived or withdrawn bytes to anyone who has it. Model-specific filenames and hashes are not authorization. There is no garbage collector, takedown workflow or demonstrated asset restore. |
| URL contract | The renderer permits relative paths below assets/images/products. The API accepts existing bundled paths for the exact model or model-scoped managed paths that exist locally. Merely saving a Supabase URL would fail those checks. Preserve legacy relative URLs where rights allow and add a controlled resolver for managed assets. |

Implementation evidence: [upload and save API](../services/api/product-management.mjs), [photo decoder](../services/api/product-photo.py), [admin editor](../js/admin/product-management.js), [public image resolver](../js/components/product-image.js), [API permission map](../services/api/permissions.mjs).

### Hosting implications

Vercel Functions have a read-only deployment filesystem and instance-local writable scratch space. Scratch files disappear when the instance stops and are unavailable to other instances. The deployed static asset tree therefore cannot serve as this uploader's shared write target. The existing API is a Node HTTP service and starts a Python/Pillow subprocess; a Vercel rollout must also supply a supported processing runtime or keep that service on a suitable separate host. A 4 MiB file becomes 5,592,408 base64 characters before JSON overhead, exceeding Vercel's default 4.5 MB request-body limit. Do not assume a larger plan-specific limit. [Vercel runtimes](https://vercel.com/docs/functions/runtimes) · [Vercel Function limits](https://vercel.com/docs/functions/limitations)

A long-running self-hosted API and static web server could share a backed-up persistent volume mounted to the same logical path. That option requires verifying reads across instances and redeploys. Drafts would still need a private location and an authorization-aware serving path. The current static folder alone does not provide those controls.

## Recommended Supabase Storage design

1. **Keep source uploads private.** Authorize through the existing admin API. Have the server allocate a unique, model-scoped staging key and record the actor and size limit. Use a short-lived signed upload to this one key or accept binary data through a size-compatible backend. Untrusted originals stay private and unservable. Apply bucket MIME/size limits in addition to the trusted decoder.
2. **Validate and record immutable assets.** Decode in a trusted worker, normalize the image and compute the digest. Write a new normalized object with overwrite disabled. On an existing key, verify byte length and digest before accepting it. Record bucket/key, model, digest, MIME, dimensions, rights status, evidence reference, approver and timestamps in restricted metadata. Approve model identity and licensing before publication. Keep database writes and storage finalization retryable; retain incomplete records for reconciliation.
3. **Serve through a stable route.** Store object keys, never expiring signed URLs, in the catalogue. Resolve a stable same-origin media URL against a published product, attached asset and approved rights, then stream it or issue a short-lived signed read. Give active managers a separate authenticated preview. Bound cache lifetime to the takedown requirement. Already cached or independently saved bytes cannot be recalled. Replace filesystem stat with an approved-asset lookup and object integrity check. Allow only the intended bucket/key formats.
4. **Restrict each operation.** Deny anonymous and STAFF upload, update, list and delete. Check manager status server-side on every request and scope any delegated write by bucket/key. Supabase service keys bypass Storage RLS and belong only on the trusted backend. Avoid upserts and general-purpose tokens. A public delivery bucket is an option only for irrevocably public, approved derivatives: anyone with a public object URL can fetch it regardless of the product row's visibility. Private objects are the safer choice for reversible publication. [Bucket access models](https://supabase.com/docs/guides/storage/buckets/fundamentals) · [Storage access control](https://supabase.com/docs/guides/storage/security/access-control)
5. **Recover files and metadata together.** Back up the PostgreSQL catalogue, asset mappings and approval metadata, and independently back up the object bytes to access-controlled storage outside the deployment. Supabase database backups cover Storage metadata only. Keep a digest manifest and document retention, key access and authorized deletion. Restore to a disposable project, verify hashes and public/private behavior, then check the detail pages. [Supabase backup scope](https://supabase.com/docs/guides/platform/backups)
6. **Acceptance before enabling the uploader.** Use synthetic images to verify a maximum-size upload, failure during processing, duplicate writes, abandoned uploads and concurrent replacement. Check denied writes for STAFF and anonymous callers, private draft reads, approved public reads and archive/takedown behavior including cache expiry. Verify the same file from a second instance and after redeployment. Independently restore one complete product gallery and compare object digests. These are proposed tests, not results of this read-only review.

| Physical integrity | The products directory contains 46 PNGs and 6 JPEGs, including the ten derivatives. All 42 original hashes match the inventory and all 40 active gallery files decoded in this review. |

The current renderer explicitly permits the owner-directed pending-rights state. The bootstrap publishes missing baseline products with those flags intact. For a commercial release, require documented permission for local hosting, display and the intended derivative processing, or serve placeholders. Keep unapproved originals, inventory manifests, bundled galleries and derivatives outside the public deployment package when access must be restricted. Hiding a thumbnail or checking product-table RLS leaves static files accessible at their URLs.
