# Owner-controlled first Super Admin bootstrap

Reviewed 2026-11-18. **Instructions only; no real account created or promoted.** Staging cleanup verified zero Auth users/profiles. Separate explicit owner approval must name the intended person/email and target project before provisioning or promotion.

## Existing safeguards

`create_disabled_profile()` creates STAFF/DISABLED regardless of user metadata. The staff API and `admin_set_staff` RPC cannot create or edit SUPER_ADMIN. ADMIN can manage only STAFF; SUPER_ADMIN may manage STAFF/ADMIN. Browser metadata, first-signup order and an email naming convention are never evidence of authority.

The original migration's commented bootstrap statement is an administrative one-time procedure, not an executable migration or public API. Do not rerun migrations or add a public bootstrap endpoint.

## Secure procedure (requires owner approval)

1. Confirm the Supabase Dashboard project is VisionTech-Staging, reference `fszrsispjxunckknphaw`. Record the approved owner email privately. Do not publish it in repository documentation.
2. Configure the exact frontend reset redirect, Supabase Auth email sender and an approved mailbox; perform the recovery email acceptance check first. See ADMIN_AUTHENTICATION_ARCHITECTURE.md. Public signup is not the bootstrap method.
3. In the private Supabase Auth administration interface, provision the specifically approved user with a unique password generated by the owner/password manager. The owner must enter/store it privately; never paste it into a chat, script, SQL file or Git. Confirm email ownership through the provider's verified flow. An invitation is also possible only after its invitation/credential setup flow is separately verified; this application's reset endpoint accepts recovery proof, not arbitrary invite/implicit tokens.
4. Record the new Auth UUID privately and verify the corresponding profile is exactly STAFF/DISABLED. Stop if an account already exists unexpectedly, email ownership is unconfirmed, the profile is absent, or any SUPER_ADMIN already exists. Resolve ambiguity rather than promoting another user.
5. An authorized database administrator can execute the following guarded one-time transaction in the **confirmed staging** SQL Editor after substituting the approved UUID/email. The template below has not been executed. Keep filled-in SQL outside Git and avoid copying credentials into it.

```sql
begin;
lock table public.profiles in share row exclusive mode;
do $$
declare
  target_id uuid := '<OWNER_APPROVED_AUTH_UUID>';
  approved_email text := '<OWNER_APPROVED_EMAIL>';
begin
  if exists (select 1 from public.profiles where role = 'SUPER_ADMIN') then
    raise exception 'A Super Admin already exists; stop bootstrap';
  end if;
  if not exists (
    select 1 from auth.users u join public.profiles p on p.id = u.id
    where u.id = target_id and lower(u.email) = lower(approved_email)
      and u.email_confirmed_at is not null
      and p.role = 'STAFF' and p.account_state = 'DISABLED'
  ) then
    raise exception 'Approved identity/profile was not verified';
  end if;
  update public.profiles
    set role = 'SUPER_ADMIN', account_state = 'ACTIVE'
    where id = target_id;
end $$;
commit;
```

6. Verify only that UUID now has SUPER_ADMIN/ACTIVE. Keep an owner-approved private operational audit record of who authorized/executed bootstrap and when; the direct bootstrap SQL does not automatically create a login event.
7. Have the owner use the configured recovery flow to choose a private password if needed, sign in, confirm the profile and dashboard permissions, then sign out and confirm access is denied. Never send an existing or new password to the assistant.
8. Create additional individual staff accounts through the authorized staff workflow; do not share the bootstrap password. Test least privilege with a separate staff account. MFA requires a supported challenge implementation before enforcement; this milestone does not claim MFA support.

## Failure handling

If provisioning or verification fails, stop and inspect the exact account. Do not mass-delete users, disable RLS, promote arbitrary users, reset the database or repair migration history. A partially provisioned disabled account is not authorized to use the dashboard. Revoke/disable only the specifically identified account with owner approval if recovery is needed.
