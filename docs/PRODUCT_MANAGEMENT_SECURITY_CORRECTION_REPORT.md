# Prompt 11B — product management authorization

The versioned editor and both legacy product RPCs now share one database field guard. The guard compares the old and proposed record, denies changes outside an ordinary-field allowlist, and checks every attached private asset against the model. Legacy create and update delegate to the same versioned RPC. Legacy update callers must now send `expected` inside their patch. Stale or missing versions cannot overwrite another editor's work. The admin API checks the active session, role and origin and rejects protected or unknown record keys.

| Fields or operation | Permitted authority |
| --- | --- |
| Create an eligible model, edit name, brand, copy, category/subcategory, features, specifications, resolution, featured state, SEO, attachment order, visibility | Active ADMIN or SUPER_ADMIN. New identity is validated; model and ID are immutable on edit. STAFF and anonymous users have no write permission. |
| Submit a technical source | An editor may record a candidate source. Changing technical facts invalidates prior verification and evidence for the record. Changing the name invalidates the previous official name. |
| verification, verificationStatus, specificationEvidence, verifiedOn, featureSource, officialName, source/provenance records, legacy image approval fields and all other non-allowlisted metadata | Neither admin role can set these through ordinary editing. Reviewed baseline technical metadata can be imported by trusted server-side bootstrap for a missing record. Post-bootstrap technical re-verification requires a separately reviewed maintenance change. There is no self-certification button. Existing verified metadata remains when its underlying facts are unchanged. |
| Register private bytes, immutable digests, dimensions and uploader | The server registers a validated asset with restricted INSERT column privileges. A database trigger checks and locks the uploader's active manager profile during registration. |
| Approve an exact-model photograph for commercial use | A separate review RPC requires an active SUPER_ADMIN other than the uploader and a nonempty evidence reference. Active SUPER_ADMIN can withdraw approval with a reason. Review records include reviewer, time and decision; admin activity retains each review. The owner must authenticate and retain the referenced license document. |
| Change approved/evidence/reviewed_by/reviewed_at directly | No ordinary client role. The review RPC assigns these values. Trusted database operators remain privileged. |
| Read images | Active managers can preview private derivatives. Public callers receive a derivative only if independently approved, attached to its own model, and the product is published. Original files and review evidence have no public endpoint. |

## Evidence

Local catalog inspection returned owner postgres and a pinned `pg_catalog, public, auth, pg_temp` search path for all six inspected functions. The three product RPCs and review RPC were security definers executable by authenticated callers, with internal role checks. The media registration trigger function was a definer; the record guard was an invoker. Neither trigger function granted client EXECUTE. Asset RLS was enabled. Storage had a restrictive private-bucket client policy and the bucket public bit was false.

The loopback suite exercised direct RPC field tampering as ADMIN and SUPER_ADMIN, legacy product entry points, unauthorized table writes, disabled login rejection, server validation, and direct asset metadata modification and deletion. ADMIN edited, archived and restored a product. SUPER_ADMIN created a draft and changed visibility. Ordinary editing never granted commercial approval. The separate reviewer approved and withdrew an asset; the uploader's direct self-review failed. The adjusted historical pgTAP fixture now supplies a supported category and an expected timestamp while continuing to assert both STAFF denial and authorized ADMIN edit.
